Certificacion de Entrega — Entrega 4: Contratos de interfaz y descubrimiento de servicios

Modulo 4 — Middleware y componentes distribuidos

El foco de esta entrega es formalizar como se comunican los componentes entre si: contratos de interfaz explicitos (API REST) y un mecanismo de descubrimiento de servicios, aunque sea simplificado.

Que evalua esta entrega: Que el sistema este desacoplado por contrato explicito, no por coincidencia entre los integrantes.

Checklist de la entrega

Requisito de la entrega Cumple Justificacion breve / evidencia
Los contratos de interfaz (API REST) entre componentes estan documentados formalmente. X Si   No Documentados formalmente bajo OpenAPI 3.0.3 en contracts/openapi-clinical-records.yaml, openapi-notifications.yaml y openapi-service-registry.yaml. Ademas, cada componente expone su contrato en vivo en GET /api/v1/contract y se incluye coleccion de Postman v2.1 (contracts/hoscorp-entrega4.postman_collection.json).
Cada componente puede modificarse internamente sin romper el contrato hacia los demas. X Si   No Implementado con el patron Contract Adapter / DTO (ClinicalRecordDTOV1, AuditLogEntryV1). El backend permite conmutar en caliente su motor interno (POST /api/v1/internal/switch-engine) entre v1-flat-legacy-store (plano) y v2-normalized-ehr-crypto (arbol jerarquico HL7/FHIR con sello SHA-256), manteniendo el JSON del contrato publico 100% invariante.
Hay un mecanismo de descubrimiento de servicios implementado (aunque sea simplificado). X Si   No Se implemento el microservicio dedicado service-registry (:5002). Los servicios se auto-registran al iniciar (POST /api/v1/registry/register), envian heartbeats cada 5s con control de TTL (18s) y el backend descubre dinamicamente a notification-service mediante GET /api/v1/registry/discover/notification-service con balanceo Round-Robin.
El desacople esta verificado: no depende de que los integrantes se hayan puesto de acuerdo informalmente. X Si   No Verificado mediante: 1) Validadores de esquemas en runtime que rechazan violaciones de contrato con HTTP 400 CONTRACT_VIOLATION; 2) Eliminacion de URLs hardcodeadas en docker-compose.yml; y 3) Suite automatizada scripts/test-contratos-discovery.ps1 y laboratorio en UI que verifican paridad tras mutar motores internos.
